# گزارش فاز ۸: نوبت‌دهی حضوری مزون با تقویم شمسی

- **تاریخ:** ۲۰۲۶-۱۱-۰۷
- **شاخه:** `arena/25a9d6ee-aroos-pro`
- **هدف:** BridalOS از «کاتالوگ + عکس + وضعیت امتحان مجازی» فراتر برود و مسیر واقعی کسب‌وکار مزون را ببندد: عروس ساعت آزاد می‌بیند، نوبت می‌گیرد، مزون تأیید یا رد می‌کند و هر دو طرف وضعیت را می‌بینند — بدون پیامک جعلی و بدون ادعای پرداخت آنلاین.

## ۱) کارهای انجام‌شده

### دیتابیس — `0009_appointments.sql`
- `boutique_availability`: ساعات کاری هفتگی با «دقیقه از نیمه‌شب تهران» و `weekday` ایرانی (۰=شنبه). هر روز فقط یک بازه (قید یکتا).
- `appointments`: `starts_at`/`ends_at` با `timestamptz`، وضعیت‌های `requested|confirmed|declined|cancelled|completed|no_show`، یادداشت عروس، دلیل رد، `decided_by`/`decided_at`، `cancelled_by`.
- **ظرفیت یک نوبت در هر بازه** با ایندکس یکتای جزئی روی وضعیت‌های فعال؛ رزرو هم‌زمان در سطح دیتابیس غیرممکن می‌شود.
- RLS: عروس نوبت خودش، کارکنان مزون نوبت‌های مزون خودشان. حذف فیزیکی وجود ندارد.
- اعمال: `npm run db:migrate` → «۱ مورد جدید / ۸ مورد موجود».

### منطق زمان (Contracts)
- `tehranOffsetMinutes`، `tehranInstant(dateKey, minute)`، `persianWeekdayOfDateKey`، `tehranDateKeyPlus`، `formatMinuteOfDayFa`، `formatDateKeyJalaliShort`.
- همه تاریخ‌ها در دیتابیس ISO/UTC هستند؛ شمسی فقط لایه نمایش است. هیچ ساعت محلی به‌صورت رشته ذخیره نمی‌شود.
- **یک باگ واقعی پیدا و رفع شد:** بعضی ICUها با `hour12: false` باز هم ساعت ۱۲ساعته برمی‌گردانند و محاسبه اختلاف زمانی را خراب می‌کردند (نتیجه: `-510` دقیقه به‌جای `+210`). حالا اختلاف از `timeZoneName: 'longOffset'` خوانده می‌شود و تست واحد دارد.

### API (`AppointmentsModule`)
- عروس: `POST /appointments`، `GET /appointments`، `GET /appointments/:id`، `POST /appointments/:id/cancel`.
- عمومی: `GET /public/boutiques/:slug/slots?date=` — فقط ساعت‌های آزاد/پرشده، بدون هیچ داده شخصی.
- مزون: فهرست نوبت‌ها با فیلتر وضعیت/تاریخ، `confirm`/`decline`/`complete`/`no-show`، و `GET/PUT /boutiques/active/availability` (فقط مالک و مدیر شعبه).
- قواعد سمت سرور: مزون باید `approved` باشد، لباس باید منتشرشده و متعلق به همان مزون باشد، زمان باید هم‌تراز با بازه‌های ساعات کاری باشد، حداقل `BOOKING_MIN_LEAD_MINUTES` جلوتر و حداکثر `BOOKING_HORIZON_DAYS` روز آینده، و حداکثر `BOOKING_MAX_ACTIVE_PER_BRIDE` نوبت فعال برای هر عروس.
- audit: `appointment.requested`، `appointment.confirmed|declined|completed|no_show|cancelled`، `availability.updated`.
- پاسخ ثبت نوبت همیشه `smsSent: false` + متن ثابت «پیامکی ارسال نمی‌شود».

### UI
- صفحه عمومی مزون: پنل «رزرو نوبت حضوری» با ۱۰ روز تقویم شمسی، بازه‌های واقعی، برچسب «پر شده»، یادداشت اختیاری و پیام موفقیت با لینک پیگیری.
- `/appointments`: «نوبت‌های حضوری من» — تاریخ شمسی، ساعت فارسی، وضعیت، دلیل رد، و دکمه لغو برای نوبت‌های آینده.
- `/dashboard/appointments`: پنل مزون — تأیید/رد با دلیل، «انجام شد»/«عدم حضور»، و ویرایشگر ساعات کاری هفتگی (فقط مالک/مدیر شعبه قابل ویرایش است و سرور هم همین را بررسی می‌کند).
- لینک «نوبت‌ها» در هدر سایت و دکمه «نوبت‌ها» در پنل مزون.

## ۴) آنچه این فاز **انجام نداد** (بدهی صریح)

1. **هیچ پیامکی ارسال نمی‌شود** (همان محدودیت قبلی)؛ عروس و مزون باید صفحه را باز کنند. یادآوری خودکار ۲۴ ساعت قبل نوبت وجود ندارد.
2. **پرداخت آنلاین و بیعانه نیست**؛ بیعانه/جریمه عدم حضور پیاده نشده چون درگاه پرداخت هنوز غیرفعال است.
3. **ظرفیت هر بازه یک نوبت است**؛ مزون پرترافیک نمی‌تواند هم‌زمان چند عروس را با چند کارمند بپذیرد (نیاز به ظرفیت و تخصیص کارمند).
4. **تعطیلات و مرخصی مزون مدیریت نمی‌شود**؛ مزون فقط با خاموش‌کردن یک روز کاری می‌تواند تعطیل کند (بازنویسی کل هفته لازم است).
5. **جابه‌جایی زمان (reschedule) وجود ندارد**؛ عروس باید لغو و دوباره ثبت کند.
6. **یادآوری/صف انتظار/لغو خودکار نوبت‌های تأییدنشده** پیاده نشده.
7. **گزارش‌های مزون (نرخ تأیید، عدم حضور، اشغال ساعات)** وجود ندارد.
8. **داده‌های آزمایشی:** همه مزون‌های موجود در `.data` با پیشوند «[داده آزمایشی]» هستند؛ هیچ داده واقعی ایرانی وارد نشده است.
