# گزارش فاز ۶ (بخش دوم): اجرای واقعی سیاست نگه‌داری + درخواست امتحان مجازی با وضعیت صریح

- **تاریخ:** ۲۰۲۶-۱۱-۰۷
- **شاخه:** `arena/25a9d6ee-aroos-pro`
- **هدف:** بستن دو بدهی بخش اول: (۱) «۹۰ روز نگه‌داری» به یک عملیات اجراشده تبدیل شود، (۲) تلاش کاربر برای امتحان مجازی ثبت و با وضعیت صریح `blocked` پاسخ داده شود — بدون هیچ تصویر ساختگی.

## ۱) کارهای انجام‌شده

### دیتابیس
- `0007_tryon_requests.sql`: جدول `tryon_requests` با `status` (`blocked|queued|processing|succeeded|failed`)، `status_reason` (۵ تا ۴۰۰ نویسه)، `provider`، کلیدهای خارجی به `users`/`bride_photos`/`dresses`، دو ایندکس و RLS فقط‌مالک.

### نگه‌داری داده
- `PhotosRetentionService`: حذف دسته‌ای (تا ۲۰۰ رکورد در هر اجرا) از عکس‌های گذشته از `retention_until`؛ حذف رکورد + فایل فیزیکی؛ خطای هر رکورد بقیه را متوقف نمی‌کند و شمارش `purged`/`failed` گزارش می‌شود.
- اجرای دوره‌ای درون API با `PHOTO_RETENTION_SWEEP_SECONDS` (پیش‌فرض ۳۶۰۰ ثانیه، صفر = خاموش، در `NODE_ENV=test` همیشه خاموش تا تست‌ها بی‌خبر تغییر نکنند).
- CLI برای cron: `npm run photos:sweep`.
- `POST /api/v1/admin/maintenance/photos-purge` برای اجرای دستی توسط ادمین + ثبت در audit (`photos.retention_purged`).
- UI ادمین: کارت «نگه‌داری داده» با دکمه اجرای پاک‌سازی و نمایش تعداد حذف‌شده.

### امتحان مجازی
- `POST/GET /api/v1/tryon` و `GET /api/v1/tryon/:id`؛ بررسی مالکیت عکس و انتشار لباس با مزون تأییدشده.
- پاسخ صریح: `status: "blocked"`، `statusReason` فارسی، `aiConfigured: false`، `provider` از `AI_TRYON_PROVIDER`.
- `/api/v1/meta` حالا `ai.provider` را هم اعلام می‌کند.
- پنل `TryOnPanel` در صفحه لباس: ورود → بدون عکس (لینک بارگذاری) → دکمه واقعی → نمایش هشدار «هیچ تصویری ساخته نشد» با شناسه پیگیری. هیچ تصویری هرگز نمایش داده نمی‌شود.

## ۵) ریسک‌ها و بدهی فنی

1. **بدون صف، حتی با provider هم throughput کنترل‌شده نیست**؛ پیش از فعال‌سازی AI باید صف + محدودیت مصرف (credit) اضافه شود.
2. **پاک‌سازی فقط عکس عروس را پوشش می‌دهد**؛ رسانه لباس و audit_logs سیاست نگه‌داری ندارند.
3. **`purgeExpired` در هر اجرا حداکثر ۲۰۰ رکورد** پاک می‌کند؛ برای حجم بالا باید تا اتمام صف حلقه بزند (در CLI با اجرای مکرر cron قابل مدیریت است).
4. **درخواست‌های `blocked` می‌توانند انبار شوند**؛ نیاز به سیاست نگه‌داری برای خود `tryon_requests`.
5. **`AI_TRYON_PROVIDER=dev-watermark`** فقط برای تست مسیر آینده است و رفتار سرویس را تغییر نمی‌دهد (همچنان `blocked`) — این عمدی است تا ادعای خروجی واقعی نشود.

## ۶) تصمیم‌های نیازمند تأیید مالک

1. آیا سیاست نگه‌داری `tryon_requests` و `audit_logs` هم باید تعریف شود (مثلاً ۱۲ ماه)؟
2. آیا پیش از فعال‌سازی AI، سقف مصرف (credit) برای هر عروس تعیین می‌شود؟
3. برای فعال‌سازی واقعی: کدام provider (با توجه به محدودیت تحریم/جغرافیایی و هزینه) مجاز است تا بنچمارک ۳۰–۵۰ لباس اجرا شود؟

## ۷) گام بعدی پیشنهادی

**فاز ۷: صف پردازش و آماده‌سازی provider** بدون کلید واقعی به این شکل: رابط `TryOnProvider` + پیاده‌سازی `DevWatermarkProvider` (خروجی با واترمارک و برچسب «آزمایشی») پشت فلگ صریح، صف داخلی مبتنی بر جدول با worker، محدودیت نرخ، و وضعیت‌های `queued/processing/succeeded/failed` واقعی — با این قید که هیچ نتیجه‌ای به‌عنوان خروجی AI واقعی به کاربر نمایش داده نشود مگر provider تجاری تأییدشده متصل شود.
